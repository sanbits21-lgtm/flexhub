# Security

What protects FitzyClub, how each protection behaves, which setting controls it, and what is still
open. Settings are listed in [CONFIGURATION.md](./CONFIGURATION.md).

Children's and members' personal data (names, phones, photos, health notes, payments) is in here,
so these protections are meant to hold up, not just exist.

## Sessions: access and refresh tokens

Signing in gives two things:

- an **access token**, valid **15 minutes**, sent with every request;
- a **refresh token**, which can only be used to get the next pair.

| | Website and member web app | Mobile app |
|---|---|---|
| Access token lives | in memory only (never in `localStorage`) | in memory (and the secure store, for a fast start) |
| Refresh token lives | an **`httpOnly` cookie** the page cannot read, `SameSite=Strict`, `Secure` over HTTPS, and sent only to its own `/refresh` and `/logout` addresses | the device's secure store (`SecureStore`) |

How it behaves:

- **Rotation.** Every refresh retires the old refresh token and issues a new one. Only a hash of
  the token is stored on the server, so a database leak hands out no working sessions.
- **Theft detection.** If a *retired* token is presented more than 20 seconds after it was
  replaced, that whole login is ended for everyone holding it. (The 20-second grace covers a lost
  reply or two browser tabs.)
- **Limits.** A login ends after 30 days unused, or 180 days even if used daily.
- **Re-checks.** A refresh repeats the sign-in checks: a deactivated person, a suspended gym, an
  unapproved gym, or someone on another gym's own address is refused.
- **Cross-site safety.** The cookie is also only honoured when the request carries a custom
  header a foreign page cannot add.
- **Ends sessions:** logging out, **Sign out of all devices** (member Profile; `POST /logout-all`),
  changing your own password (other devices only), a manager re-issuing a member's app login, a
  forced trainer password reset, deactivating a person, and a member deleting their account.
- **No network is not "signed out".** The apps keep the session through a lost connection and only
  end it when the server explicitly refuses the refresh.

## Login protection

- **Per-address limit:** 10 failed sign-ins per 15 minutes per network address.
- **Per-account lockout:** 5 wrong passwords within 15 minutes lock that account for 15 minutes
  (then 30, then 60). It answers HTTP 429 with a message and `Retry-After`, and **refuses even the
  correct password while locked**. A correct sign-in resets the count. Members are tracked per
  gym address, so one gym's attacker cannot lock another gym's member.
- **No account enumeration.** A made-up email or member code locks and answers exactly like a real
  one, a password check is always performed (so response time does not give it away), and the
  confirmation "resend" always answers the same.
- **Sign-up** answers identically for a new email and an existing one. The existing account's owner
  gets an email instead ("you already have an account", at most once per 10 minutes; or a fresh
  confirmation link if they never confirmed, at most once a minute).

## Passwords

- Stored with bcrypt. Length 8 to 72. The platform owner created from the environment needs 12+.
- A password is **refused** when it is on a list of common passwords (also with digits or symbols
  added, so `Welcome2024!` and `Password123!` fail), a number/alphabet/keyboard run, repetitive, or
  contains the person's **own name, email name or phone number**.
- Applied everywhere a person picks one: sign-up, changing your own, new staff, new gym owners,
  new platform admins, the environment-created super-admin, and a member password if staff supply one.
  Passwords generated by the system (member app logins, trainer resets) are random.

## Rate limits

| What | Limit |
|---|---|
| Sign-up | 5 per hour per address (`SIGNUP_PER_HOUR`) |
| Email confirmation and resend | 20 per hour per address |
| Sign-in | 10 failed per 15 minutes per address |
| Session refresh | 120 per 15 minutes per address |
| Everything else under `/api` | 300 per 15 minutes per address |

These are mounted **before** the public routes (a route that answers first never reaches a limiter
placed after it, which once left the sign-up limits doing nothing; a test now pins it).
They depend on `TRUST_PROXY` being right: see the post-deploy check in [RENDER.md](./RENDER.md).

## Content-Security-Policy

The server tells the browser which sources a page may use. If an attacker ever got a `<script>`
into a page, the browser would not run it.

- Scripts and styles only from the site's own files, plus **two exact inline blocks allowed by
  hash** (the dark-mode script in `index.html` and the privacy page's style block). The hashes are
  computed from the built files at start-up, so a rebuilt page is picked up by a restart. No
  `unsafe-inline` or `unsafe-eval` anywhere.
- Connections only to the site itself; images from the site, `data:`, `blob:` and any `https:`
  address (gyms can show a logo from anywhere); no frames, no plugins, no `<base>` changes, forms
  only to the site, and the site cannot be framed by others.
- **`CSP_MODE`**: `enforce` (default), `report-only` (log, block nothing) or `off`.
- The browser reports each blocked item to `POST /api/csp-report`, and the server logs one line,
  `[csp] blocked <what> by <directive> on <page>`. That endpoint accepts no login, is limited to
  10 KB, and only a short summary is logged.
- **If a page goes blank or something stops loading after a change**, set `CSP_MODE=report-only`,
  read the `[csp]` log lines, and allow the new source in `backend/middleware/csp.js`. If a new feature
  needs another site (for example a map or a payment widget), add it there deliberately.
- Verified in a real browser against every owner, member and platform page; an injected inline
  script, external script, outbound request and plain-http image were all blocked.

## Request and data hardening

- **Request bodies:** 100 KB by default; 5 MB only for bulk member import and profile photos.
- **Validation:** every write is validated (Zod) before it reaches a controller. Query values that
  are not plain strings (`?branchId[$ne]=x`) are rejected.
- **Tenant isolation:** every query is scoped to the caller's gym and branch, writes overwrite any
  client-supplied ids, and creating a member, payment or session checks that the branch, plan and
  trainer belong to the same gym.
- **Photos:** only JPEG, PNG and WebP (checked by file signature), at least 200x200 pixels (read from the file's own header; a file whose size cannot be read is refused) and at most 1 MB, for members and for staff (`/api/profile/photo`), random file names,
  served only through the API to people allowed to see them.
- **CSV safety:** exported failed-row files neutralise cells beginning with `=`, `+`, `-` or `@`.
- **Email links** are built from `PUBLIC_URL`, never from a request's `Host` header. The server
  will not start in production without it (on Render it falls back to Render's own address).
- **Headers and runtime:** Helmet defaults (HSTS, no-sniff, no framing), CORS closed in production
  unless `CORS_ORIGIN` is set, the container runs as a non-root user with a read-only filesystem
  apart from the uploads folder.
- **Audit trail:** sensitive changes (approvals including "Approve anyway", renewals, package
  edits, password resets) are written to the audit log.

## Dependencies

- Backend production: the Express `qs` issue is fixed. One `uuid` advisory remains and does not
  apply (the code only uses `v4()`, and the advisory is about passing a buffer to other versions).
- Website production: no known advisories (`react-router` upgraded to v7).
- Build tooling still reports advisories (`esbuild`'s dev server, `glob`, `minimatch`,
  `deepmerge`). They are not part of what users run; they need a build-tool upgrade.
- Re-check any time with `npm audit --omit=dev` in `backend/` and `frontend/`.

## Before you go live

1. `JWT_SECRET` is a long random value (Render generates one).
2. `PUBLIC_URL` is your real address (or you are on Render and using its address).
3. Email works: register a test gym and receive the confirmation.
4. The first super-admin is created, its password changed, and `SUPER_ADMIN_PASSWORD` removed.
5. **Rotate the MongoDB Atlas password** if it was ever weak, and restrict Atlas network access
   (Render's addresses, not `0.0.0.0/0`).
6. Run the RENDER.md post-deploy checks (client address, photo persistence).
7. Try five wrong passwords on a test account and see the lock message; try a weak password and
   see it refused.

## If you think a session was stolen

- One person: deactivate them, or reset their password (this ends their sessions); members can use
  **Sign out of all devices**.
- Everyone: changing `JWT_SECRET` ends every **access token** immediately, but refresh tokens
  live in the database, so also empty the `sessions` collection. Everyone then signs in again.

## Forgot password

Staff, owners and platform admins use **Forgot your password?** on the login page; members use the same link on the
member sign-in page. The flow is built so that it cannot be used to attack an account or to learn who has one:

- Asking for a link always gets the same answer, whether or not the address has an account. Only a real, active account
  with an email address is emailed (and an owner who has not confirmed their address gets the confirmation link
  instead, not this).
- The link carries a random 256-bit token. Only its hash is stored, it works **once**, and it lasts **one hour**. Asking
  again replaces it, so an older link stops working.
- An account is emailed at most once a minute, and each network address can ask 10 times an hour.
- A member whose email is shared with others (a family) gets one link per member, each naming its member ID.
- Using the link applies the same password rules as everywhere else, then ends **every login** of that person
  (access tokens issued earlier stop working and every refresh token is deleted), lifts any sign-in lock, writes an audit
  entry, and emails them that the password changed. It does not sign anyone in.
- The reset page removes the token from the address bar as soon as it loads, and the site sends
  `Referrer-Policy: no-referrer`.

## Terms of Service

New gyms tick **I agree to the Terms of Service and the Privacy Policy** to register; the server refuses a registration
without it (`TERMS_REQUIRED=off` disables the rule) and stores the version they agreed to and when. The text is in
`backend/public/terms.html`. It is a **starting point written from how the product works, not legal advice**: have a
lawyer review it, then update `TERMS_VERSION` and `TERMS_UPDATED` in `backend/utils/terms.js` whenever it changes.

## What is not covered (known gaps)

- **"Forgot password" works by email only.** A member with no email address on file cannot use it: a manager
  re-issues their app login at the front desk. There is no SMS or WhatsApp code.
- **No two-factor authentication.**
- **No list of signed-in devices** (only "sign out of all devices" for members).
- **The mobile app** typechecks and its token logic is tested on the server, but it has not been
  exercised on a physical device with the new sessions.
- **A burst of simultaneous wrong guesses** can slip a few extra tries past the lockout check
  before the lock lands; the per-address limit still bounds it.
- No malware scanning of uploads (they are restricted to small, signature-checked images), no
  web-application firewall, and no automated dependency alerts.
